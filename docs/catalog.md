# Каталог заданий и Git-снимки

## Статус и источник

Git-адаптер, парсер, fingerprint и CLI реализованы в `adapters/catalog/`, синхронизация с публикацией — в `application/catalog.py`. Этот документ задаёт их контракт; наличие реализации не заменяет реальные smoke/security-проверки развёртывания. Общие технологии, порты и значения эксплуатационных настроек заданы в [архитектуре](architecture.md). Связанные контракты: [посылки и хранилища](submissions.md), [безопасность](security.md), [порядок реализации](implementation.md).

Единственный исходный репозиторий — [kr0sh512/OS-tasks](https://github.com/kr0sh512/OS-tasks). Его постоянный `repo_id` — точная UTF-8-строка `https://github.com/kr0sh512/OS-tasks`, без завершающего `/` и `.git`. Это идентификатор источника, а не произвольный URL, получаемый из HTTP-запроса пользователя. Редирект или смена транспортного адреса сами по себе не меняют идентификатор.

Зафиксированный пример формата взят из [commit ab6760a333dc1b452aac6e2cb37ffa9c850c4c3c](https://github.com/kr0sh512/OS-tasks/tree/ab6760a333dc1b452aac6e2cb37ffa9c850c4c3c):

```text
1. Пример первой темы/
  1/
    task.md
    tests/
      1.in
      1.out
      2.in
      2.out
  2/
    .gitkeep
2. Пример второй темы/
  .gitkeep
```

Содержимое [`1. Пример первой темы/1/task.md`](https://github.com/kr0sh512/OS-tasks/blob/ab6760a333dc1b452aac6e2cb37ffa9c850c4c3c/1.%20%D0%9F%D1%80%D0%B8%D0%BC%D0%B5%D1%80%20%D0%BF%D0%B5%D1%80%D0%B2%D0%BE%D0%B9%20%D1%82%D0%B5%D0%BC%D1%8B/1/task.md):

```markdown
# Назание задачи

здесь содержится описание задачи в .md формате

---

# Название подсказки

Первая подсказка, разделённая "---"

---

# Название второй подсказки

также описание
```

Опечатка «Назание» сохранена как в исходнике. Все четыре файла `tests/1.in`, `tests/1.out`, `tests/2.in`, `tests/2.out` имеют нулевую длину. Это две допустимые пары пустого входа и ожидаемого пустого вывода. Каталог задачи `1. Пример первой темы/2` и тема `2. Пример второй темы` содержат только `.gitkeep` и не становятся активными задачами. Пример иллюстрирует структуру и подсказки, но не является содержательным набором проверок C-программ: успешный результат на нём не доказывает решение какой-либо реальной C-задачи.

## Структура и идентичность

Корень снимка содержит каталоги тем, внутри темы расположены каталоги задач. Путь задачи имеет ровно два компонента: `<тема>/<задача>`. Обязательные имена регистрозависимы: `task.md` и `tests`. Описание — обычный UTF-8-файл, а тесты — обычные файлы в непосредственном каталоге `tests`:

```text
<тема>/<задача>/task.md
<тема>/<задача>/tests/<N>.in
<тема>/<задача>/tests/<N>.out
```

`N` — непустая последовательность ASCII-цифр; вход и выход образуют пару только при полном совпадении строки `N`. Например, `01.in` не образует пару с `1.out`. Пары `01.in`/`01.out` и `1.in`/`1.out`, если обе существуют, являются разными тестами; порядок определён ниже. Пропуски номеров допустимы, перенумерация не нужна. Регистр расширения менять нельзя. Нулевая длина одного или обоих файлов допустима; отсутствие файла не равно пустому файлу. Для доступности проверки нужна хотя бы одна полная пара, а не просто существующий каталог `tests`.

`.gitkeep` не является тестом или описанием. Каталоги, в которых нет ничего, кроме `.gitkeep` и таких же вложенных каталогов-заготовок, не создают задачи и не дают доступ к отправке решения. Пустая тема без задач не появляется как тема с доступной проверкой. Каталог на уровне задачи становится кандидатом при наличии `task.md`, `tests` с данными кроме `.gitkeep` либо других непустышечных записей; недостаток обязательных частей делает кандидата недоступным, а не успешно проверяемым.

Иные обычные файлы вне `tests` могут сопровождать задачу и не становятся тестами; файлы корня, например README, не являются темами. Вложенные каталоги под `tests`, неожиданные расширения и неполные пары делают соответствующую задачу недоступной. `.gitkeep` внутри `tests` разрешён как служебная запись, не входящая в число тестовых пар. Данные из вложенного каталога не поднимаются автоматически на уровень задачи; вложенные темы и альтернативный поиск `task.md` не поддерживаются.

Для каждой задачи вычисляется:

```text
task_id = lowercase_hex(SHA256(UTF8(repo_id) || 0x00 || UTF8(task_relative_path)))
topic_id = lowercase_hex(SHA256(UTF8(repo_id) || 0x00 || UTF8(topic_relative_path)))
```

Пути относительны корню Git-дерева, без начального и конечного `/`, с разделителем `/`. `task_relative_path` — путь каталога задачи, например `1. Пример первой темы/1`; путь темы — `1. Пример первой темы`. Вход не содержит commit, tests digest, заголовка Markdown или номера в отсортированном списке. Нельзя добавлять завершающий NUL, перевод строки или нормализовать Unicode перед хешированием. Переименование любого компонента пути создаёт новый ID; изменение `task.md` или тестов при прежнем пути не меняет ID. Исходные имена и пути сохраняются отдельно для UI и диагностики, а не восстанавливаются из хеша. ID темы и задачи принадлежат разным типам сущностей.

### Порядок и Unicode

Темы, задачи внутри темы и тестовые пары сортируются естественно, а не строково: `2` раньше `10`, `Тема 2` раньше `Тема 10`. Порядок не зависит от locale процесса, порядка обхода Git или файловой системы.

Ключ сортировки строится из чередующихся текстовых и числовых частей имени. Только для этого ключа последовательности Unicode-пробелов, включая NBSP (`U+00A0`) и узкий NBSP (`U+202F`), заменяются одним обычным пробелом; крайние пробелы ключа удаляются; текст сравнивается после Unicode casefold. Последовательность десятичных Unicode-цифр категории `Nd` — числовая часть; её значение определяется десятичными значениями цифр без ограничения машинным целым. Числовые части сравниваются по значению, текстовые — по Unicode-кодовым точкам; при разном типе части числовая предшествует текстовой, при равном префиксе более короткий ключ идёт первым. Окончательный tie-breaker — лексикографическое сравнение исходных UTF-8-байтов полного относительного пути. Поэтому `01` и `1`, разные формы Unicode и разные пробелы не сливаются даже при одинаковом первичном ключе. Реализация должна зафиксировать версию Unicode, используемую этим ключом.

Правила ключа не изменяют имена в UI, ID, пути файлов или digest. Unicode-пробел внутри имени не является разделителем аргументов или компонентов пути. Недопустима обработка списка файлов через разбиение по пробелам или строкам; Git-пути читаются по протоколу с NUL-разделителями.

## Markdown: описание и подсказки

Используется CommonMark-парсер markdown-it-py из архитектуры. Сначала разбирается весь `task.md` с сохранением диапазонов исходных строк. Разделитель подсказок — только узел `thematic_break` непосредственно в корне документа, исходная строка которого равна ровно `---` после удаления только окончания строки LF или CRLF.

Недостаточно найти строку регулярным выражением. Не являются разделителями:

- `---` внутри fenced или indented code block;
- подчёркивание setext-заголовка, например строки `Название` и `---`, разобранные как один heading;
- горизонтальная черта внутри blockquote, списка или другого вложенного блока;
- `> ---`, `- - -`, `***`, ` ---`, `--- ` либо текст с inline `---`.

Описание содержит всё до первого подходящего разделителя. Каждый последующий сегмент — отдельная подсказка; сами разделители удаляются. Если разделителей нет, весь документ является описанием, подсказок нет. Пустое описание и пустые сегменты не выбрасываются: их позиции сохраняются. Номер `N` подсказки — её позиция среди сегментов после первого разделителя, начиная с 1.

Название подсказки берётся из первого корневого heading данного сегмента независимо от его уровня; heading внутри цитаты или блока кода не подходит. Inline-разметка заголовка преобразуется в безопасный обычный текст для `summary`. Выбранный heading удаляется из тела подсказки, остальной текст, в том числе перед ним, сохраняется. При отсутствии heading или пустом текстовом названии используется `Подсказка N`. Название задачи в списке остаётся исходным именем каталога; заголовок описания не влияет на идентичность.

Каждая подсказка отображается отдельным `<details><summary>…</summary>…</details>`. При первоначальном показе все закрыты: атрибута `open` нет. Общего атрибута `name`, принудительно объединяющего элементы в аккордеон, нет; раскрытие одной подсказки не закрывает другую. Наличие в Markdown строк `<details open>` не даёт источнику управлять состоянием этих элементов.

Результат рендеринга описания и тел подсказок проходит HTML-санитизацию nh3 перед вставкой в шаблон. Нельзя доверять upstream HTML, атрибутам событий, URL-схемам, CSS или скриптам; запрещены исполняемые вставки и обход санитайзера через raw HTML. Служебные `details`/`summary` создаёт шаблон приложения, не исходник; одноимённые исходные HTML-элементы и их управляющие атрибуты не допускаются в очищенном фрагменте. Текст названий тем, задач, подсказок и диагностик экранируется контекстно. Остальная политика допустимых тегов, ссылок и ресурсов должна соответствовать [спецификации безопасности](security.md), без второго обходного пути рендеринга.

## Безопасное получение неизменяемого снимка

`catalog-sync` с периодом `CATALOG_POLL_SECONDS` из архитектуры получает вершину основной ветки upstream; выбранный commit затем фиксируется полным object ID. Все чтения этого импорта относятся к одному commit и его tree, а не к изменяемому рабочему каталогу или продолжающей двигаться ссылке. Снимок включает commit, дерево, разобранный каталог, ошибки отдельных задач и tests digest. После построения эти данные неизменяемы.

Git-адаптер обеспечивает следующие ограничения:

1. Адрес источника задаёт приложение, а не пользовательская посылка. Git запускается массивом аргументов без shell; пути и имена не интерполируются в команды, опции или выражения `rev:path`.
2. Получение выполняется в изолированном служебном Git-хранилище с контролируемыми конфигурацией и окружением: без пользовательских/system hooks, template hooks, credential helper, пользовательского SSH-командного кода и executable filters. Hooks отключены явно, а не предположением об их отсутствии.
3. Используется только необходимый HTTPS-транспорт; запрещены `file`, `ext` и рекурсивный обход протоколов. Не выполняются checkout содержимого, Git hooks, smudge/clean-фильтры, LFS-команды, скрипты из репозитория или submodule update. `.gitmodules` не является инструкцией к исполнению.
4. Записи `symlink` и `gitlink`/submodule в импортируемом Git-дереве запрещены и отклоняют новый снимок целиком. Нельзя следовать ссылке даже ради чтения `task.md` или `tests`. Обычный executable bit файла не разрешает его выполнение импортёром.
5. Пути валидируются как последовательности UTF-8-компонентов. Запрещены абсолютные пути, `.`/`..`, пустые компоненты, NUL и неоднозначные для целевого размещения варианты. Обратный слеш не используется как альтернативный разделитель; адаптер не должен допускать превращение имени в выход за корень при материализации. Unicode-нормализация и нечувствительность к регистру не могут молча объединять разные Git-пути.
6. Дерево и blobs читаются структурированно, с проверкой типов объектов, размеров и object ID. `git cat-file` обрабатывается как ограниченный бинарный протокол: заявленный размер проверяется до выделения памяти/чтения, фактическое количество байтов и разделители проверяются, EOF и ошибка дочернего процесса не считаются пустым файлом.
7. Обязательны конечные лимиты времени Git/fetch/cat-file, диска служебного хранилища, объёма получаемых объектов, количества и глубины записей дерева, длины путей, размера отдельного blob/Markdown и суммарных прочитанных байтов. Таймаут или превышение — ошибка импорта, не усечение данных. Защита диска должна действовать и во время fetch, а не только после него.

Численные Git/cat-лимиты заданы внутренними константами адаптера; параметры реализации перечислены ниже. Это не новые пользовательские или deploy-настройки и не повод расширять таблицу настроек архитектуры. Проверка этих ограничений не заменяется лимитами пользовательского исходника или stdout песочницы.

Для исполнимости задачи импорт также проверяет транспортные пределы runner из [спецификации безопасности](security.md): `MAX_TEST_STDIN_BYTES = 1048576` байт исходного stdin одного run-запроса и `MAX_EXPECTED_OUTPUT_BYTES = 65536` байт ожидаемого вывода (равен `MAX_OUTPUT_BYTES`). Превышение любого предела делает задачу недоступной; тест не обрезается и не пропускается. Это внутренние ограничения, не новые env-настройки. Оба предела входят в `judge_policy_digest`; смена пределов меняет политику и исключает повторное использование прежнего кэша.

Commit pinning обеспечивает согласованность снимка, но не аутентифицирует авторов задач или людей, отправляющих решения. Имена из профиля сессии не удостоверяют личность. Тексты заданий, тестовые байты и все пользовательские исходники остаются недоверенными.

### Реализация, CLI и дисковый формат

`checker-catalog` начинает первую синхронизацию немедленно, затем после каждой попытки
ждёт `Settings.catalog_poll_seconds` (`CATALOG_POLL_SECONDS`, по умолчанию 60 секунд).
`checker-catalog --once` импортирует и публикует один снимок; ошибка даёт ненулевой
exit status. Оператор может добавить `--ref main`, имя другой ветки или полный
commit ID. `--ref` не является URL и не может менять источник. Источник берётся
только из `Settings.tasks_repository_url` / `TASKS_REPOSITORY_URL`: принимается
HTTPS без credentials, query и fragment. HTTP-переадресации запрещены; при переносе
репозитория оператор явно обновляет транспортный адрес. Произвольного HTTP API
для импорта репозитория нет. `repo_id` остаётся указанной выше постоянной строкой.

Каталогу необходимы Linux/POSIX `flock`, `O_NOFOLLOW`, resource limits, Git с HTTPS
и доверенным CA bundle, права записи sync-процесса в `CATALOG_ROOT`, а также transient
PostgreSQL (`TRANSIENT_DATABASE_URL`). Ни runner token, ни архивная БД ему не нужны.
Web/worker должны видеть тот же volume по тому же абсолютному пути, но не выполнять
fetch на пользовательском запросе. URL `file:`, локальный путь, SSH, ext и HTTP
отклоняются также в тестовой конфигурации production-класса.

`GitCatalog(settings)` предоставляет:

- `await import_snapshot(ref=None) -> CatalogSnapshot`: возвращает полностью
  построенный снимок с `generation=0`; публикация не меняет этот объект;
- `load_snapshot(snapshot_id) -> CatalogSnapshot`: синхронное чтение дискового DTO
  с проверкой формата, ID, commit, root path и конечного размера JSON;
- `load_test(snapshot, task, index) -> (stdin_bytes, expected_bytes)`: синхронное
  чтение исходных бинарных байтов, включая нулевую длину. Проверяет принадлежность
  задачи, availability, индекс и каждый компонент пути через `O_NOFOLLOW`.

Снимок хранится в `CATALOG_ROOT/snapshots/<snapshot_id>/`. Служебный JSON имеет
фиксированное имя `snapshot.json`; все записи upstream находятся только под
`tree/`. Поэтому файл upstream с именем `snapshot.json` не может заменить metadata.
Пути `TestCase.input_path`/`expected_path` относительны корню снимка и начинаются с
`tree/`. Envelope JSON содержит `format=1`, `parser_version=catalog-v1`,
`unicode_version` и поле `snapshot` с сериализованным доменным DTO. Commit — полный
40-символьный SHA-1 Git object ID; каждый прочитанный объект дополнительно проверяется
по Git SHA-1 framing. Git object format SHA-256 пока не принимается.

`snapshot_id = SHA256(UTF8(repo_id + NUL + commit + NUL + parser_version + NUL +
unicode_version))`. Используются Unicode tables `unicodedata.unidata_version`
интерпретатора (Unicode 16.0.0 для Python 3.14); версия зафиксирована в envelope и
идентичности конкретного снимка. Обновление интерпретатора не пересортировывает
сохранённый DTO: оно создаёт другой snapshot ID. `tests_digest` от этой версии не
зависит. Сортировка чисел использует длину и лексикографическое сравнение десятичных
строк без ограничения машинным целым или лимитом Python `int(str)`.

Материализация выполняется во временном каталоге, файлы и каталоги синхронизируются
`fsync`, после чего read-only дерево переносится атомарным rename. Импорт защищён
как `asyncio.Lock`, так и межпроцессным `flock` на `.import.lock`; публикация в одном
`CatalogSynchronizer` также входит в его блокировку, исключая обгон import/publish.
Дополнительно CLI держит `.publisher.lock` весь срок жизни, включая ожидание БД
и polling: второй daemon или `--once` на том же volume немедленно завершается с
ошибкой вместо конкурирующей публикации старого commit. Для ручного `--once`
оператор сначала останавливает постоянный `catalog-sync`.
Оставшиеся после аварии приватные `.fetch-*` удаляются только под import lock.
Опубликованные snapshots импортёр не удаляет: удержание до подтверждённой уборки
всех использующих их работ важнее автоматической экономии диска.

`CatalogSynchronizer.sync()` вызывает только `store.publish_catalog(snapshot)`.
Именно хранилище назначает generation атомарно вместе с инвалидированием, а не JSON
файл или локальный mutex. Ошибка импорта не вызывает публикацию пустого DTO;
периодический процесс пишет причину и известный commit попытки в журнал, продолжает
polling и не заменяет последний валидный указатель.

### Внутренние защитные лимиты

Лимиты заданы константами адаптера, без новых env-настроек:

| Ограничение | Значение |
| --- | --- |
| Wall time fetch | 60 с |
| Команда Git / ответ одного cat-file / завершение cat-file | 10 с |
| Бюджет Git-импорта, проверяемый также при материализации | 120 с |
| Ожидание межпроцессного import lock | 120 с |
| CPU каждого Git-процесса / hard address-space limit | 60 с / 512 МиБ |
| Hard file-size limit каждого Git-процесса | 64 МиБ на файл |
| Служебное хранилище активного fetch | 128 МиБ, контролируется каждые 25 мс во время fetch |
| Требуемый остаток свободного диска во время fetch | не менее 128 МиБ |
| stdout и stderr обычной Git-команды | не более 2 МиБ каждый |
| Заголовок cat-file | не более 128 байт, включая LF |
| Blob / Markdown / один tree или commit object | 8 МиБ / 1 МиБ / 2 МиБ |
| Совокупно прочитанные Git objects | 64 МиБ, с повторными чтениями |
| Записей дерева / глубина / UTF-8 путь / UTF-8 компонент | 10000 / 16 / 1024 / 255 |
| JSON metadata | 128 МиБ |
| stdin теста / ожидаемый stdout теста | 1048576 / 65536 байт |

Дисковый монитор действует **во время** fetch, а не только после него; при
превышении лимита убивается вся process group. Это оперативный предел с интервалом
измерения, а не filesystem quota: объём может кратковременно превысить 128 МиБ
между измерениями. Дополнительный hard per-file `RLIMIT_FSIZE` действует независимо
от частоты монитора. На volume необходим запас для fetch и атомарной материализации,
а также для удерживаемых опубликованных снимков; нехватка места приводит к ошибке,
не к усечённому или частичному импорту. Каталог не предназначен для размещения
служебных Git-данных на безлимитном общем системном разделе без эксплуатационного
контроля свободного места.


## Глобальный tests digest

`TestsFingerprint.calculate(tree)` вычисляет один SHA-256 для всего снимка, не отдельный digest только выбранной задачи или только доступных задач. Область включает все каталоги с точным именем `tests` во всём Git-дереве и все их потомки, в том числе у неактивных и ошибочных задач и вне распознанной структуры тем. Если каталоги вложены друг в друга, каждая запись включается один раз. Другие пути не входят в digest.

Каноническое представление имеет версионный префикс `os-sol-checker-tests-v1` с завершающим NUL, затем записи в лексикографическом порядке исходных UTF-8-байтов полного относительного пути. Для каждой записи последовательно добавляются:

1. длина пути как беззнаковое 64-битное big-endian число и точные UTF-8-байты пути;
2. тип/режим Git как ровно шесть ASCII-цифр (`040000` для каталога, `100644` или `100755` для обычного файла);
3. длина содержимого как беззнаковое 64-битное big-endian число и точные байты файла; для каталога длина равна нулю и байтов содержимого нет.

Размеры проверяются на допустимость до кодирования; переполнение не разрешено. Записи каталогов включаются наряду с файлами. Поэтому пустой каталог `tests`, добавление/удаление/переименование каталога или файла, смена типа/режима записи, изменение входа либо ожидаемого выхода меняют digest. `.gitkeep`, дополнительные файлы и вложенные каталоги внутри области также учитываются, хотя не являются тестовыми парами. Запрещённые типы записей не получают «условный digest»: такой снимок вообще не публикуется.

Git обычно не сохраняет пустые рабочие каталоги: сравнивать нужно именно опубликованное tree. Если пустой tree-каталог представлен в Git-объекте, его запись учитывается; если пустая локальная директория не попала в commit, она не существует для импорта. Пустышка `.gitkeep` делает существование каталога наблюдаемым по Git и сама входит в digest, когда находится внутри `tests`. Добавление первого каталога `tests` и отсутствие любых таких каталогов дают разные представления.

Не влияют на digest: mtime/ctime, порядок обхода, время fetch, commit metadata, Git object IDs сами по себе, изменения `task.md` и иных файлов вне области `tests`. Переименование темы или задачи с тестами меняет пути тестов и потому меняет digest. Нельзя хешировать только конкатенацию содержимого: это потеряло бы пути, границы, пустые файлы и каталоги.

## Публикация, generation и конкурентность

Временная БД хранит единственный текущий указатель `(snapshot_id, commit, tests_digest, generation)`. Читатель получает согласованный снимок; нельзя прочитать описание из одного commit и тесты из другого. Порядок публикации:

1. Получить и полностью проверить новый неизменяемый снимок вне текущего указателя. Завершить разбор всех задач и вычисление digest до транзакции публикации.
2. Захватить общую блокировку generation в `checker_transient`. Её используют также приём посылки/чтение кэша и finalize worker; это один контракт сериализации, а не независимые локальные mutex разных процессов.
3. В одной транзакции временной БД опубликовать новый указатель. Если digest изменился, монотонно увеличить generation, удалить результаты старого поколения из кэша и временные посылки старого поколения с их исходниками, отменить старые очереди и активные работы. Записи `session_last_submissions` сохраняют прежний UUID с `available:false`, без сохранения удалённого исходника/результата. Для активных работ сохранить отдельные достаточные сведения об уборке, не требующие существования удалённой посылки.
4. После commit инициировать прекращение старых stage и удаление их песочниц. Доступ к старому результату или новое выполнение старой очереди уже запрещены, даже если физическая уборка ещё не завершилась. Факт незавершённой уборки устойчиво хранится, чтобы после сбоя worker продолжил удаление.

Первая успешная публикация создаёт generation `1`. Повторная публикация того же digest не увеличивает generation и не очищает кэш/посылки: например, исправление описания не отменяет выполняющиеся проверки. Уже принятая посылка при этом сохраняет свой исходный неизменяемый snapshot/context; новый UI читает новый снимок. Если видимые метаданные задачи изменились без смены тестов, кэш не делает недоступную задачу доступной: валидность текущей задачи проверяется до cache hit.

Профиль сессии, cookie и данные человека не удаляются при смене тестов. История последней посылки по задаче в `session_last_submissions` сохраняет прежний UUID и `available:false`; UI показывает «История недоступна», не подставляет другую посылку и не выдаёт удалённые исходник или результат. Отсутствие последней посылки и недоступная прежняя посылка — разные состояния. Постоянная база `checker_archive`, её исходники и ранее сохранённые факты успеха не очищаются и не переписываются.

Worker фиксирует generation и snapshot при получении работы. Перед каждым новым stage и обязательно перед finalize он проверяет актуальность. Finalize захватывает ту же блокировку generation, повторно сверяет generation и только при совпадении допускает публикацию актуального терминального результата и запись в текущий кэш. Проверка и соответствующий commit во временной БД выполняются под одной блокировкой. Завершившийся после переключения worker старого поколения не публикует актуальный `ACCEPTED` и не пишет новый кэш; временная посылка недоступна/инвалидирована, выполняется уборка. Старые тесты не продолжаются ради получения архивного успеха.

Архив и временная БД разные: общей PostgreSQL-транзакции между ними нет и она не требуется. Архив хранит исторический факт прохождения всех тестов в конкретном неизменяемом context, а не актуальный ответ кэша. Полностью завершённая успешная проверка может быть идемпотентно записана только со своим исходным commit, tests digest, generation и политикой проверки; её нельзя перепривязать к новому поколению или считать свидетельством актуального `ACCEPTED`. Идемпотентность и восстановление частичного finalize определяются в [контракте посылок](submissions.md).

Архивный commit, уже начавшийся при прежнем поколении, может завершиться после переключения только со старым context и остаётся историческим фактом. Это не возвращает удалённую посылку в UI, не заполняет новый кэш и не отменяет инвалидирование. При недоступном архиве текущая посылка может находиться в `archive_pending`; после инвалидирования новые архивные retries не запускаются. Неопределённый исход уже начатого commit не даёт права повторять запись от имени нового поколения. Публикация снимка не ждёт доступности архива или разрешения исхода такого commit: generation-lock защищает согласованность временной БД, а не создаёт распределённый барьер между базами.

Неизменяемый старый snapshot хранится, пока на него ссылается активная работа, незавершённый finalize или запись уборки. Отмена очереди не является доказательством завершения jail. Физически удалять snapshot можно только после завершения/отмены всех использующих его работ и подтверждённой runner уборки их jail и артефактов. Публикация не должна ожидать сетевого подтверждения уборки runner внутри транзакции; обязанности worker по конечным лимитам и уборке описаны в [безопасности](security.md).

## Ошибки и доступность

Сбой сети, fetch, лимита ресурсов, чтения объекта, UTF-8 или структурно неоднозначный импорт отклоняет новый снимок целиком. К неоднозначности относятся небезопасные пути/типы, столкновение путей после необходимых для размещения преобразований, невозможность однозначно сопоставить записи дерева и неполученное полное дерево. Нельзя публиковать уже разобранную половину тем, использовать старые тесты с новым описанием либо заменять отсутствующие байты пустыми.

После ошибки синхронизации продолжает действовать последний полностью валидный snapshot с прежним digest/generation; диагностическое состояние сообщает причину и commit неудачной попытки, если он известен. Readiness может оставаться true при наличии такого снимка. На первом старте без валидного снимка readiness false, каталог не объявляется готовым и приём проверок запрещён. Пустой, но полностью и корректно разобранный репозиторий отличается от ошибки импорта: у него может быть готовый пустой каталог, но нет доступных задач.

Локальная неполнота задачи — отсутствующий/нечитаемый как UTF-8 `task.md`, отсутствие `tests`, отсутствие хотя бы одной пары, лишние записи в `tests`, неполная пара или неправильный обязательный тип вроде обычного файла вместо каталога `tests` — даёт видимую недоступную задачу с конкретной безопасной диагностикой. Остальные однозначно разобранные задачи снимка могут быть доступны. Под ошибкой UTF-8 всего импорта выше понимаются пути/структурные данные, а ошибка содержимого отдельного Markdown локальна задаче. Тестовые файлы бинарные: невалидный UTF-8 в них не является ошибкой.

Недоступная распознанная задача остаётся видимой на HTML-странице с причиной и отключённой отправкой; API возвращает её availability и причину, а не маскирует существующую задачу ответом 404. Она не попадает в очередь, не получает `ACCEPTED` через пустой цикл тестов и не обслуживается старым cache hit. Скрытая заготовка `.gitkeep` не маскируется под недоступную полноценную задачу. Приоритет общей ошибки безопасности/ресурсного ограничения выше локальной ошибки: например, symlink внутри одной задачи отклоняет весь новый снимок, а не только делает задачу недоступной.

## Наблюдаемые критерии реализации

Регрессионные тесты каталога находятся в `tests/unit/test_catalog*.py`, а безопасная копия структуры upstream-примера — в `tests/fixtures/catalog/upstream/`. Они охватывают две пустые пары, скрытые `.gitkeep`, numeric pairing и его ошибки, Unicode natural sort, стабильность ID, точные CommonMark-разделители, HTML/URL-санитизацию, глобальный digest с пустыми деревьями и режимами, реальные локальные Git objects с небезопасными типами/путями, ограниченный cat-file framing, дисковое чтение без symlink, синхронизацию и сохранение последней публикации при ошибке. Локальные Git repositories используются только как parser fixtures; production fetch остаётся HTTPS-only. CLI smoke с настоящим upstream, интеграционная атомарность `publish/finalize`, архивная гонка и удержание старых snapshots проверяются отдельно после интеграции со store/worker. Перечень регрессий не является утверждением, что эти проверки уже выполнены в конкретном развёртывании.
