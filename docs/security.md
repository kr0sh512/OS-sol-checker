# Безопасность runner и протокол исполнения

## Статус и модель доверия

Runner, API, nsjail profiles, rootfs build, независимый watchdog и внешний PID1 supervisor реализованы. Это не утверждение о пройденном production security smoke: фактическая проверка требует отдельного Linux x86-64 хоста с rootful Docker, enforcing AppArmor и делегированными cgroup v2. Rootless Podman, отсутствие AppArmor/nsjail или cgroup delegation не поддерживаются; runner отказывает закрыто. Топология, команды и честный статус испытаний — в [развёртывании](deployment.md), общий контракт — в [архитектуре](architecture.md).

Worker — доверенный контроллер: он читает выбранный неизменяемый снимок каталога, сравнивает вывод и записывает результаты в БД. Runner — отдельный доверенный сервис с GCC, nsjail и двумя минимальными rootfs. Он получает исходник и stdin только текущего теста, но не читает каталог или БД и не знает ожидаемый вывод. Web и catalog-sync не имеют доступа к управляющему API runner.

Недоверенными считаются исходник, процессы решения, результаты работы компилятора, stdout/stderr и исполняемый артефакт. Компилятор обрабатывает враждебный ввод, поэтому компиляция также выполняется в новой jail. На каждый тест создаётся следующая новая jail; процессы, writable-файлы, mounts и IPC предыдущей стадии не переиспользуются. Между стадиями только runner хранит ограниченный артефакт в своей приватной области вне дочерних jail.

nsjail использует общее с хостом ядро Linux. Это не виртуальная машина и не доказательство отсутствия побега через уязвимость ядра, компилятора, nsjail или Docker. Rootful Docker и права управляющего процесса runner увеличивают последствия его компрометации. Выделенный хост без посторонних секретов, своевременные обновления и проверка профилей обязательны; нельзя обещать абсолютную безопасность.

## Изоляция каждой стадии

Следующие требования относятся и к компиляции, и к исполнению:

- Новые namespaces: network (`clone_newnet`), user (`CLONE_NEWUSER`), PID (`CLONE_NEWPID`), mount (`CLONE_NEWNS`), IPC (`CLONE_NEWIPC`) и UTS (`CLONE_NEWUTS`). Отдельная сеть без внешних интерфейсов и маршрутов; не предоставлять доступ к сети runner, DNS, хосту, metadata endpoints или соседним сервисам, в том числе по IPv6.
- Фиксированные непривилегированные UID/GID и проверенные отображения user namespace; без дополнительных групп. Все capabilities дочернего процесса сброшены, `no_new_privs` включён; setuid/setgid-файлы и доступные устройства отсутствуют.
- Минимальный read-only rootfs задаётся allowlist: компилятор и необходимые заголовки/библиотеки для compile, совместимый загрузчик и необходимые библиотеки для run. Не монтировать внешний `/`, корень runner, каталог приложения, Docker socket, дерево каталогов заданий или весь cgroup filesystem хоста.
- Единственные writable-области — отдельные ограниченные tmpfs стадии, суммарно не больше `SANDBOX_TMP_MIB=32`. Они не общие между стадиями или посылками. Запрещены произвольные mounts и доступ к диску хоста. Приватное хранилище артефактов runner также ограничено по объёму и не монтируется целиком в jail.
- Дочерний `/proc`, если нужен, относится только к новому PID namespace. Jail не видит процессы, `/proc`, окружение или файловые дескрипторы supervisor/watchdog. API listener, управляющие соединения, `RUNNER_TOKEN`, credentials БД, чужие артефакты и ожидаемые ответы недоступны через файлы, argv, env, fd и mounts.
- Применяется отдельный seccomp allowlist каждой стадии; ограничения внешнего контейнера дополняют, но не заменяют фильтр внутри jail. Нельзя автоматически отключать seccomp, AppArmor или namespace ради совместимости задачи.
- Запуск — фиксированный argv без shell, фиксированные cwd и минимальная явно заданная среда. Создание процесса использует `close_fds`; наследуются только явно разрешённые pipe ends для fd 0/1/2. Лишние концы pipe закрываются в родителе и ребёнке. Ни HTTP socket, ни управляющий канал runner не наследуется.
- Stdin решения — pipe с байтами только текущего теста; после передачи он закрывается. Stdout и stderr — отдельные pipes без TTY, ограничиваемые во время чтения. Ребёнок не пишет служебный ответ API: его вывод никогда не интерпретируется как verdict или сообщение доверенного монитора.

Образ runner неизменяем и содержит nsjail, compile/run rootfs, конфигурации nsjail и seccomp. Контекст проверки фиксирует `runner_image_digest` и `sandbox_profile_digest`; последний покрывает конфигурации nsjail, содержимое rootfs, фильтры seccomp и версию nsjail. Флаги и все лимиты, включая внутренние пределы stdin/expected и транспортных сообщений, входят в `judge_policy_digest`. Декларируемый digest должен быть проверен при старте, а не слепо принят из запроса worker. Несовпадение или отсутствие любого обязательного механизма даёт readiness false и отказ 503; запасного менее изолированного исполнения нет.

## Ресурсы и время

Runner получает только явно делегированное поддерево cgroup v2. Каждая стадия имеет отдельную дочернюю cgroup с ограничениями всего дерева процессов:

| Ресурс | Начальная политика |
| --- | --- |
| Память | `memory.max`: 256 МиБ; tmpfs и учитываемая ядром память входят в бюджет. Swap запрещён через `memory.swap.max=0`. |
| Процессы | `pids.max`: 64, включая потомков. |
| CPU | `cpu.max`: квота одного логического CPU, например `100000 100000`; wall timeout действует независимо. |
| Writable scratch | Не больше 32 МиБ суммарно на стадию. |
| Stdout + stderr | Не больше 65536 исходных байт суммарно на стадию. Превышение останавливает стадию. |
| Исполняемый артефакт | Не больше 1048576 байт. |

`RLIMIT_NOFILE`, `RLIMIT_FSIZE`, `RLIMIT_CORE=0` и подходящие дополнительные rlimits усиливают защиту, но не заменяют cgroup: ограничения отдельного процесса не ограничивают fork-дерево или общую память стадии. Выход за лимит tmpfs также не заменяет memory limit.

Внешний контейнер runner имеет конечные совокупные memory/PID/CPU/tmpfs limits для `N=4` одновременных стадий плюс отдельно рассчитанный бюджет supervisor, HTTP API, watchdog и приватных артефактов. Его лимиты должны вмещать заявленную параллельность, но оставаться жёстким пределом потребления хоста; без расчёта внешнего бюджета только четыре внутренних лимита не защищают хост. Приватное хранилище рассчитано максимум на N артефактов по 1 МиБ и ограниченные метаданные; временные копии при передаче учитываются отдельно. Общие ресурсы application и БД также ограничиваются при развёртывании.

На компиляцию от запуска процесса — 10 секунд monotonic wall time, на один тест — 2 секунды. Весь активный жизненный цикл от claim worker, включая резервирование, I/O, создание jail и cleanup, имеет бюджет 60 секунд; очередь в него не входит. Worker передаёт runner оставшийся бюджет с консервативным вычетом ограниченного времени доставки запроса. Runner при резервировании фиксирует собственный monotonic deadline не позже этого остатка; TTL не продлевается между запросами. Сетевые чтения/записи и подготовка стадии тоже ограничены остатком общего бюджета.

Таймеры runner независимы от времени жизни HTTP-запроса и worker. Отдельный доверенный watchdog вне jail прекращает stage по deadline, даже если worker потерян или клиент отключился. Supervisor внешнего контейнера следит за API и watchdog: при их отказе прекращает обслуживание и завершает все дочерние процессы. Внешний контейнер имеет собственный PID namespace, не PID namespace хоста; смерть его supervisor должна приводить к остановке всех потомков, а не оставлять независимые jail.

Timeout — обязательное решение контроллера остановить дерево процессов в заданное время, но физическое завершение является best effort при зависшем ядре или замороженном хосте. Нельзя заявлять безусловное физическое уничтожение ровно за 60 секунд. Пока остановка и уборка не подтверждены, слот занят; при невозможности подтвердить cleanup runner становится неготовым.

## Внутренний HTTP API

`RUNNER_URL=http://runner:8081` доступен только worker через отдельную внутреннюю сеть одного хоста. Порт не публикуется. Все маршруты, включая list/delete и локальную health-проверку, требуют `Authorization: Bearer <RUNNER_TOKEN>`; сравнение секрета выполняется constant-time. Секрет обязателен, отсутствует в web, catalog-sync, jail и логах. Health проверяется локально и возвращает только готовность без конфигураций, handles и секретов. Передавать bearer по открытому межхостовому соединению нельзя; расширение за пределы этой сети требует аутентифицированного шифрованного транспорта.

Запросы не могут задавать shell-команды, произвольные пути, argv, env, флаги GCC, mounts, образы или ослабления защиты. `policy_id` выбирает только заранее установленную неизменяемую политику. Runner проверяет её наличие, digest и допустимость, а worker сверяет подтверждённый контекст с контекстом посылки.

`RUNNER_TOKEN` содержит минимум 32 байта. Авторизация выполняется до обработки execution metadata, включая неизвестные маршруты. После резервирования compile/run/delete дополнительно требуют `X-Execution-Handle` (непрозрачный handle из ответа, до 128 ASCII-байт). Этот handle привязан к UUID execution и не заменяется UUID посылки. DELETE неизвестного UUID остаётся 204 после bearer-аутентификации. Приватный bearer даёт worker право list/recovery всех своих executions; web и catalog-sync не получают его.

| Метод и путь | Контракт |
| --- | --- |
| `GET /v1/policy` | Аутентифицированный ответ — shared `JudgePolicy` без обёртки. Worker проверяет computed `.digest`, фиксирует policy в transient DB; runner не читает БД. При неготовой изоляции — 503. |
| `POST /v1/executions` | JSON не больше 4096 байт: UUID посылки `submission_id`, `policy_id`, `remaining_seconds` в диапазоне `(0, 60]`. Runner атомарно проверяет готовность/политику и резервирует один из N слотов на весь execution. Ответ 201: новый UUID `execution_id`, непрозрачный handle, подтверждённые digests/лимиты и оставшийся TTL. UUID и handle связаны с посылкой и текущим жизненным циклом runner. |
| `POST /v1/executions/{id}/compile` | `Content-Type: application/octet-stream`, raw body исходника не больше 102400 байт; ровно 102400 разрешено. Одна компиляция на execution. Ответ 200 с outcome содержит ограниченные diagnostics и при успехе непрозрачный `artifact_handle`, но не исполняемые байты и не путь к файлу. Артефакт остаётся у runner. |
| `POST /v1/executions/{id}/run` | `Content-Type: application/octet-stream`, raw body — stdin одного теста, включая любые нулевые и не-UTF-8 байты. `X-Artifact-Handle` длиной не больше 128 ASCII-байт указывает артефакт именно этого execution и submission. Ответ 200 содержит outcome одного теста; разрешены последовательные run после успешной compile. |
| `GET /v1/executions` | Только активные handles: submission/execution UUID, состояние, подтверждённый контекст и остаток TTL. Не возвращает исходники, stdin или артефакты. Список ограничен N записями. Нужен для восстановления контроллера, а не для доступа учащихся. |
| `DELETE /v1/executions/{id}` | Идемпотентная отмена: прекращает текущий I/O, останавливает cgroup, убирает ресурсы. 204 только после подтверждённой уборки; уже удалённый/неизвестный UUID также даёт 204 после авторизации. Внутренний таймер продолжает работать независимо от соединения. |

Состояния одного execution сериализованы: резервирование → compile → готовый артефакт → последовательные run → удаление. В одном слоте не более одной стадии. Параллельный, повторный compile, run до успешной compile или run с чужим artifact handle отклоняется; успешная стадия не освобождает слот посылки. Поля JSON и размеры заголовков ограничены, лишние поля не дают новых полномочий. Общий размер заголовков — не больше 8192 байт; произвольные chunked/streaming тела учитываются по фактически прочитанным байтам, отсутствие Content-Length не отменяет лимиты.

### Бинарные данные и конечные размеры

- Compile body ограничен `MAX_SOURCE_BYTES=102400`; run body — внутренним `MAX_TEST_STDIN_BYTES=1048576`. Ограничения применяются до неограниченного буферизования, в том числе при медленной передаче и неверном Content-Length.
- Импорт каталога отклоняет задачу целиком, если хотя бы один `.in` превышает `MAX_TEST_STDIN_BYTES=1048576` либо `.out` превышает эффективный предел `min(MAX_EXPECTED_OUTPUT_BYTES, MAX_OUTPUT_BYTES)`, начально `min(65536, 65536)` байт. Не обрезать тесты и не принимать частичный набор. При изменении политики каталог заново проверяется: нельзя принять задачу с expected длиннее доступного stdout. Сами expected в runner не передаются. Ограничения на файлы при импорте не заменяют ограничения API.
- Outcome кодирует stdout и stderr раздельными JSON-полями `stdout_base64` и `stderr_base64`. Сначала применяется общий предел 65536 исходных байт; base64 не является дополнительным каналом вывода. Worker строго декодирует их в bytes до точного сравнения, не нормализует UTF-8, переносы строк или пробелы. Размер JSON outcome ограничен 98304 байт, включая base64 и ограниченные метаданные.
- Ответ compile не экспортирует артефакт. Перед его чтением runner останавливает и reaps всё дерево compile stage, подтверждает пустоту cgroup, исключая продолжающуюся запись ребёнком. Только затем доверенный процесс открывает фиксированное имя относительно доверенного directory fd, без path traversal и с `O_NOFOLLOW`, проверяет через fd обычный тип файла и размер и копирует не больше 1048576 байт в приватное хранилище. Symlink, нестандартный тип и превышение размера отклоняются. Даже такой артефакт остаётся недоверенным; для run в свежую jail попадают только он и stdin текущего теста, не вся область артефактов.
- Outcome содержит `status`, exit code/signal, monotonic wall time и структурированную ресурсную причину от доверенного монитора: timeout, memory/PID/output/artifact limit либо ошибка инфраструктуры. Нельзя определять OOM по одному exit 137 или доверять строке, напечатанной ребёнком. JSON/diagnostics тоже считаются недоверенными при отображении пользователю.

Ошибки протокола возвращают ограниченный JSON без исходника и секретов:

| HTTP status | Значение и действие worker |
| --- | --- |
| 400 / 415 | Некорректная схема/тип тела или недопустимый TTL; ошибка интеграции, не verdict решения. |
| 401 | Нет/неверный bearer; никаких метаданных execution в ответе. |
| 404 | Неизвестный execution/artifact для compile/run; чужой handle не раскрывается. DELETE остаётся идемпотентным. |
| 409 | Конфликт состояния: стадия уже идёт, compile уже выполнен, execution закрывается либо artifact принадлежит другому execution. |
| 429 | Все N слотов заняты; применяется только к резервированию. Worker оставляет/возвращает job в состояние очереди, не отмечает active и не создаёт вторую очередь ожидающих внутри runner. |
| 413 | Превышен предел тела/заголовков/служебного сообщения; чтение и стадия безопасно прекращаются. |
| 503 | Политика, профиль, namespaces/cgroup или cleanup недоступны/не прошли проверку; readiness false для системной неисправности. Это infrastructure_error, не вина решения. |

Неуспешная компиляция, runtime_error и штатные ресурсные остановки передаются как outcome, а не маскируются под HTTP 503. Причины и приоритет terminal outcome фиксируются событиями доверенного монитора: ошибка до запуска процесса — infrastructure_error; исчерпание общего активного бюджета — submission_timeout; локальный wall timeout исполнявшейся стадии — compile_timeout/run_timeout. Worker не кэширует инфраструктурные ошибки.

Worker сопоставляет outcome публичным verdict из [контракта посылок](submissions.md). `accepted` и `wrong_answer` определяет только worker, не runner. Превышение лимита артефакта — `compile_error` с отдельной безопасной диагностикой; принудительная остановка из-за PID limit — `compile_error` на compile либо `runtime_error` на run, с явным `resource_reason: "pids"`. Не обозначать эти причины как OOM. Ошибки ENOSPC/EAGAIN, которые программа сама корректно обработала без принудительной остановки, не являются автоматическим отрицательным verdict.

## Отмена, сбои и восстановление

Авторитетный семафор из `N=4` слотов находится в runner. Worker имеет собственный предел N и единственный активный планировщик под PostgreSQL advisory lock на отдельном соединении. Даже при ошибочном запуске второго worker локальный предел runner не превышается. Сам runner запускается строго в одном экземпляре: два независимых семафора не образуют общий лимит.

При потере advisory-lock соединения worker прекращает claims и отменяет принадлежащие ему executions. Новый владелец lock до первого claim вызывает `GET /v1/executions`, сопоставляет handles с состоянием временной БД и отменяет устаревшие, незавершённые и не принадлежащие новому контроллеру executions. Если временная БД потеряна, отменяются все найденные handles. До подтверждения этой уборки новые jobs не запускаются. Недоступность runner блокирует начало исполнения, а не включает локальный запуск.

Потеря ответа compile/run не доказывает, что стадия не выполнялась. Нельзя вслепую повторять такой запрос или пересоздавать execution: worker запрашивает отмену и завершает посылку как infrastructure_error. Восстановить результат без отмены допустимо только после реализации и доказательства точного восстановления состояния/исхода той же операции; текущий контракт этого не обещает. Потеря ответа резервирования также требует сверки списка по submission UUID и уборки, а не создания дубликата. Перезапуск runner теряет все временные handles и артефакты; незавершённые посылки становятся infrastructure_error, не запускаются автоматически заново.

На первом провале теста, смене generation, любом terminal outcome, исключении и отмене worker вызывает destroy в `finally`. Runner независимо делает cleanup при deadline и собственных ошибках: закрывает stdin/output/control I/O, применяет `cgroup.kill` ко всему дереву, ждёт завершения и reaps потомков, проверяет пустоту cgroup, снимает mounts, удаляет tmpfs и приватные файлы execution. `fork`, `setsid` и выход первоначального процесса не оставляют фоновых потомков. Артефакт сохраняется только между успешно завершёнными стадиями одной посылки; stage cleanup выполняется и в этом случае. Следующая стадия и освобождение слота допустимы лишь после подтверждённого cleanup предыдущих ресурсов. Ошибка уборки изолирует слот и переводит runner в неготовое состояние, а не выдаёт его следующему решению.

### Усыновлённые потомки и asyncio

После выхода процесс-зомби уже может отсутствовать в `cgroup.procs`. Поэтому API-процесс в режиме subreaper отдельно собирает завершившихся усыновлённых потомков через `/proc/self/task/*/children` и `waitpid(WNOHANG)`, не полагаясь на сохранённый список cgroup PID. Прямые процессы, принадлежащие asyncio child watcher, учитываются до завершения `Process.wait()` и исключаются из общего reaping. Создание/регистрация процесса и reaping сериализованы, включая отмену во время spawn.

Две регрессии запускают только доверенные Python-процессы: зомби, уже отсутствующий в `cgroup.procs`, должен быть собран, а exit status прямого asyncio-ребёнка не должен быть перехвачен. Они не доказывают работу namespace, cgroup.kill или изоляцию C-программы.


## Компилятор и сравнение

Начальный argv с фиксированными именами:

```text
gcc -std=gnu17 -O2 -pipe -Wall -Wextra -Wformat=2 -Werror=format-security
    -fstack-protector-strong -D_FORTIFY_SOURCE=2 -fPIE -pie
    -Wl,-z,relro,-z,now /work/main.c -o /work/main -lm -pthread
```

Это один массив аргументов, не shell-строка. Общего `-Werror` нет; обычное предупреждение не делает корректное решение неуспешным. Пользовательские опции GCC не принимаются. GCC/libc compile rootfs совместимы с run rootfs, их содержимое фиксируется образом/профилем. Изменение flags, rootfs, nsjail, лимитов или comparator изменяет контекст проверки и исключает старый кэш.

Worker сравнивает stdout с `.out` точно по байтам, включая пробелы и завершающий LF. Stderr не сравнивается с expected, а показывается как ограниченная безопасно экранированная диагностика. Nonzero exit/signal либо ресурсная остановка имеют приоритет над совпавшим stdout. После первого непрошедшего теста следующие не запускаются. Перед допуском курса проверить реальные задачи и fork/wait, pipe, signals, mmap, pthread; требование внешней сети, доступа к хосту или запрещённых syscall не является поводом ослабить политику.

`pause` разрешён внутренними фильтрами обеих стадий и внешним seccomp для сигнальных задач. Это не отменяет wall/deadline watchdog и не является подтверждением полной совместимости курса без реального runner smoke.

## Данные и интерфейс приложения

- Web/worker/catalog-sync работают non-root. Credentials разделяются по сервисам и ролям; web не читает архив успешных исходников. В jail нет ни одного прикладного секрета.
- В логи не писать исходники, stdin, ожидаемые ответы, cookies, токены, имена/группы или полный stderr. Достаточно submission UUID, task ID, generation, политики, bounded infrastructure reason и verdict.
- Временная БД и runner scratch не резервируются; архив имеет постоянное хранилище, backup и проверку восстановления. Каталог — отдельные неизменяемые снимки: sync пишет, web/worker читают; runner к ним не подключается.
- Публичный интерфейс требует HTTPS, body/rate limits, проверки принадлежности посылки сессии и CSRF. UUID посылки не является авторизацией; временное имя/группа не подтверждает личность.
- Markdown без raw HTML проходит allowlist-санитизацию. Ссылки разрешают только безопасные http/https или same-origin относительные URL; javascript/data/file и protocol-relative URL запрещены. Внешние изображения и HTML-вставки не загружаются, файлы изображений из Git не публикуются автоматически. Скрипты только same-origin без inline; CSP запрещает object/frame и сторонние script origins.

## Реальная цепочка исполнения и проверка политики

`checker-runner` должен быть PID1 приватного PID namespace внешнего контейнера. Он запускает отдельные API и watchdog процессы, контролирует их pipe-heartbeat и при смерти/зависании прекращает обслуживание, убивает всех потомков независимо от process group/session и завершает PID1. Watchdog каждые 10 мс проверяет неизменяемый execution deadline, stage deadline и `memory.events`; первое событие остановки атомарно фиксируется в закрытом registry. HTTP disconnect не отменяет watchdog и не продлевает TTL.

До готовности API проверяет enforcing `checker-runner` AppArmor, seccomp mode 2, `no_new_privs`, конечные aggregate limits делегированного subtree и manifest. Затем действительно исполняет только доверенный заранее собранный `checker-probe` через **оба** nsjail profiles. Probe проверяет различие network/user/PID/mount/IPC/UTS/cgroup namespaces, UID/GID mapping 65534:65534:1, отсутствие supplementary groups/capabilities/лишних fd, read-only корень, отсутствие секретов/cgroups и внешних интерфейсов. Пользовательского C в startup probe нет.

`runner-manifest.json` создаётся при сборке из настоящего nsjail binary, обоих rootfs, trusted jail init/probe и полного дерева nsjail/seccomp profiles. На старте пересчитываются SHA-256 всех файлов, пути, типы, размеры, mode/UID/GID и symlink targets; extra/missing/changed files и небезопасные типы/права отклоняются. nsjail 3.4 закреплён source commit `079d70dda4aa1edd9512cfd25ff1e47e316dc355`; kafel закреплён его gitlink. `RUNNER_IMAGE` обязан иметь `@sha256:<64 lowercase hex>`: это доверенное оператором имя запущенного immutable образа, а не digest, полученный от недоверенного worker. Docker socket ради самопроверки образа не выдаётся.

Trusted stage launcher помещает себя в отдельную ограниченную cgroup **до** exec nsjail и создания jail. Во время подготовки и уборки у execution остаётся слот. `/work` — свежий bounded tmpfs; `/tmp` внутри rootfs ссылается только на `/work/tmp`. Корень jail read-only. Run получает отдельную read-only bind mount только своего файла `/work/main`; исходник, private artifacts, expected и каталоги никогда не монтируются. Контрольная cgroup не монтируется внутрь jail.

Launcher проверяет не только успешную запись: его собственный PID обязан читаться обратно из kernel `cgroup.procs` именно ожидаемого delegated leaf **перед** exec nsjail. Дети наследуют эту membership, nsjail не управляет отдельными cgroups; startup probe дополнительно подтверждает новый cgroup namespace и строго `0::/` в `/proc/self/cgroup`. Ошибка placement либо namespace proof — not-ready, без fallback на другую hierarchy.

Внутри jail `checker-init` сохраняет отдельный status pipe, устанавливает non-dumpable и перед exec закрывает этот fd у недоверенного ребёнка. Только init сообщает доверенному контроллеру START и exit/signal. Чтение `/proc/1/fd` защищено kernel ptrace access check; ptrace/process_vm/pidfd_getfd отсутствуют в allowlist. Stdout/stderr не являются служебным протоколом. Отсутствие trusted completion без структурированного resource stop — infrastructure_error, а не ошибка компиляции по тексту nsjail.

Незагружаемый submitted artifact имеет отдельный доверенный `EXEC_ERROR <errno>` и даёт runtime_error; отказ exec самого GCC/probe — infrastructure_error. `prlimit64` для PID1 запрещён, чтобы ребёнок не менял лимиты monitor. Startup probe не ограничивается унаследованным `Seccomp:2`: forked socket/unshare/ptrace probes должны реально получить SIGSYS под **внутренним** фильтром; проверяются все пять capability sets, точная минимальная среда и невозможность открыть monitor status fd.

Успех outcome называется `completed` (`exit_code=0`, `signal=null`). Остальные статусы: `compile_error`, `runtime_error`, `compile_timeout`, `run_timeout`, `submission_timeout`, `memory_limit`, `output_limit`, `infrastructure_error`. `resource_reason` уточняет `memory`, `pids`, `output`, `artifact`, `timeout` либо `cancelled`; accepted/wrong_answer вычисляет только worker. Достигнутый `pids.max`, который программа сама обработала и завершилась успешно, не превращается в ошибку. `clone3` возвращает ENOSYS, чтобы libc использовала фильтруемый clone; namespace flags в clone запрещены.

API проверяет общий 8192-byte header budget, 4096-byte reservation JSON, source/stdin limits по фактически полученным chunks и monotonic read deadline. HTTP parser также ограничивает незавершённые headers; malformed oversized parser input может быть отклонён до ASGI как HTTP 400. Outcome до 98304 байт, общий stdout+stderr до policy.output_bytes. `RunnerClient` строго декодирует base64, проверяет подтверждённую policy и размеры, не повторяет compile/run. Потерянный reservation response сверяется через list по submission UUID и отменяется, но никогда не вызывает второй POST.

Незавершённый HTTP header ограничен тремя секундами, включая slowloris с постоянными маленькими chunks. Весь ASGI request/response имеет конечный wall budget `submission_deadline_seconds + 10`; при зависшей записи уже начатого ответа соединение закрывается, а stage остаётся под независимым watchdog. В клиенте общий транспортный timeout охватывает всю передачу, не только отдельный read. Из передаваемого remaining budget вычитается целиком ограниченное время доставки reservation (до пяти секунд), не произвольная малая константа.

Artifact читается после cgroup.kill, wait/reap и подтверждённой пустоты cgroup. Фиксированный `main` открывается через directory fd с O_NOFOLLOW/O_NONBLOCK, допускается только regular single-link nonempty file до policy.artifact_bytes. FIFO, symlink, directory, hardlink и oversized output отклоняются без зависания. После copy снимается mount и удаляется stage tmpfs; ошибка cleanup карантинирует execution и выключает readiness. DELETE отвечает 204 только после полной уборки private state.

Кодовые API/FD/artifact tests не доказывают изоляцию. `tests/security/test_runner_isolation.py` выполняет недоверенный C **только** через явно указанный готовый runner API и пропускается без соответствующего opt-in окружения. Реальные namespace/kill/OOM/seccomp/AppArmor и supervisor-failure smoke должен выполнить оператор до открытия приёма решений.
