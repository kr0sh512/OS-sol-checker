# Посылки, хранение, HTTP и интерфейс

## Назначение и статус

Это контракт будущей реализации, а не описание работающего сервиса. Здесь нет SQL, обработчиков, шаблонов или готового запуска пользовательских программ. Обязательны [архитектура](architecture.md), [каталог](catalog.md), [безопасность](security.md) и [план реализации](implementation.md). Все исходники и данные профиля недоверенные. Имя и группа — самоописание, не проверенная личность; отсутствие входа не позволяет использовать архив как доказательство авторства.

## 1. Приём и идентичность

1. Принимается `multipart/form-data` с ровно одной файловой частью `file`. Другие части, повторный `file`, отсутствующий файл, пустой filename и повреждённый multipart отвергаются. Метаданные профиля берутся из серверной сессии, не из multipart.
2. Расширение имени должно быть ровно `.c` с учётом регистра: `solution.c` разрешено, `solution.C`, `.cpp`, `.c.exe` — нет. MIME части не определяет язык. Имя ограничено 255 байтами UTF-8, не содержит NUL, управляющих символов, `/` или `\`; имя никогда не используется как путь, имя рабочего файла или аргумент shell. Неверное имя — `422 invalid_filename`, неверное расширение — `415 unsupported_extension`. Фиксированное внутреннее имя исходника определяет адаптер песочницы.
3. Исходник — исходные байты файла, без перекодировки, изменения переводов строк, добавления завершающего LF или удаления BOM. Размер `0..102400` байт включительно. Пустой `.c` принимается и получает результат реального компилятора (например, `compile_error`), а не ошибку загрузки. Содержимое, не являющееся корректной программой C, может быть принято и затем получить `compile_error`; сервер не подменяет компилятор проверкой текста.
4. Весь HTTP body, включая multipart-разделители и заголовки частей, ограничен `131072` байтами включительно. Приём потоковый: размер считают фактически, включая запросы без `Content-Length`; при превышении прерывают чтение, удаляют временные данные и отвечают `413`. Превышающий предел заявленный `Content-Length` можно отвергнуть сразу, но ему нельзя доверять вместо подсчёта. Для тела и файловой части действуют независимые счётчики. Нельзя сначала читать неограниченный body в память или на диск.
5. `SourceIdentity = (sha256, byte_size)`: SHA-256 вычисляется по оригинальным байтам; digest — 64 строчных hex-символа, размер — целое число байт. Равенство идентичностей не отменяет проверки совпадения доступных сохранённых байтов перед повторным использованием. Несовпадение байтов при той же паре — `503 identity_conflict`, инфраструктурное событие, без ложного попадания кэша, перезаписи blob или исполнения подозрительной записи.
6. Каждая **принятая** отправка получает новый криптографически случайный UUIDv4, созданный сервером. Одна и та же строка `id` используется сервером, клиентом, журналом статуса и квитанцией архива. Клиент не назначает идентификатор. Даже cache hit, follower и повторное нажатие создают отдельные UUID и записи. Отклонённый запрос не считается принятой отправкой и не меняет last-submission. Повтор POST после потери ответа может создать новую посылку; API не обещает идемпотентность POST.
7. В момент приёма фиксируются профиль автора, владелец-сессия и неизменяемый контекст одного согласованного снимка каталога. Данные заданий приходят только из опубликованного Git-снимка, не от клиента.

## 2. Контекст, кэш и очередь

`result_key = (task_id, generation, judge_policy_digest, sha256, byte_size)`.

`generation` — положительный монотонный номер опубликованного поколения проверки; правила его изменения и идентификаторы снимков определены в [каталоге](catalog.md). Контекст включает `snapshot_id`, `catalog_commit`, `tests_digest`, `generation`, `judge_policy_digest`, `runner_image_digest`, `sandbox_profile_digest`, `flags_digest`, лимиты и `comparator_version`. `runner_image_digest` фиксирует immutable runner image с GCC/nsjail; `sandbox_profile_digest` — конфигурацию nsjail, compile/run rootfs, seccomp и версию nsjail внутри этого образа. Всё фиксируется при приёме и не редактируется вслед за каталогом. Изменение политики проверки меняет `judge_policy_digest`; старый кэш неприменим. Компаратор первоначально требует точного побайтового совпадения.

Кэш общий для пользователей, но выдаёт только результат проверки текущей посылки. Из чужой записи не возвращаются UUID, имя, группа, исходник, имя загруженного файла или идентификатор сессии. Каждая новая посылка получает собственные владельца, snapshot профиля, время и last-submission. Публичного API исходников, списка чужих посылок или архива нет.

- В кэш попадают только доказанные окончательные `accepted` и ошибки студенческой программы, перечисленные ниже. `infrastructure_error`, `identity_conflict`, `invalidated`, промежуточный `archive_pending` и неполное исполнение не кэшируются. Кэш не является архивом.
- Наличие завершённого текущего результата даёт `cache_hit: true`. Ошибка из кэша завершается сразу. Успех из кэша всё равно требует идемпотентной записи собственного факта успеха в архив **до** публикации `accepted`.
- Для незавершённого `result_key` существует не более одного активного `queue_job`. Следующие посылки становятся followers этого задания, имеют собственные UUID, `cache_hit: false` и получают общий доказанный результат, но собственные квитанции успеха. Они не занимают новые места очереди и не запускают вторую компиляцию. После получения инфраструктурной ошибки новая отправка может создать новое задание; уже завершённые записи задним числом не меняются.
- Очередь хранится в PostgreSQL и ограничена `QUEUE_CAPACITY` (положительное целое, значение по умолчанию `1000` ожидающих уникальных заданий). Активные задания не входят в этот предел. При заполнении новый уникальный job отклоняется `503 queue_full`; cache hit или присоединение к существующему job допускаются. Проверка вместимости и создание job атомарны, не через приблизительный счётчик в web-процессе. Отдельный лимит частоты/ресурсов на сессию описывает [безопасность](security.md); followers не обходят его.
- `N = MAX_CONCURRENT_SANDBOXES`, по умолчанию `4`: глобальный предел одновременно существующих compile/run sandbox, не число web-реплик и не размер очереди. Единственный активный планировщик выдаёт слоты, один runner независимо обеспечивает авторитетный семафор N; на слот приходится не более одного stage. Внешний runner-контейнер долгоживущий, компиляция и каждый тест получают свежую jail, а не новый контейнер. Задания выбираются FIFO по моменту создания job и UUID для равных времён; follower не меняет приоритет.
- Приём одной transient-транзакцией проверяет актуальность поколения, профиль, кэш/активный job и ёмкость; создаёт submission, привязку job при необходимости и обновляет last-submission. Нельзя получить last-submission без записи посылки или потерять job после успешного ответа. Если каталог сменился до фиксации, приём повторяет выбор актуального контекста до публикации UUID клиенту.

## 3. Состояния и результаты

| `status` | Смысл | `verdict` |
| --- | --- | --- |
| `queued` | Ожидает запуска общего job | `null` |
| `compiling` | Идёт компиляция | `null` |
| `running` | Последовательное выполнение тестов | `null` |
| `archive_pending` | Успех доказан, собственная архивная запись ещё не подтверждена | `null` |
| `finished` | Окончательная проверка, архивная квитанция успеха подтверждена при `accepted` | Непустой |
| `invalidated` | Контекст больше не действителен для незавершённой проверки | `null` |

Терминальные состояния — `finished`, `invalidated`; при них polling прекращается. Нормальный путь: `queued → compiling → running → archive_pending → finished`. Возможны прямой `finished` из кэша, ошибка компиляции без `running`, переход любого незавершённого состояния в `invalidated`. `archive_pending` никогда не показывается как окончательный успех. У followers отражается стадия общего job; архивная финализация каждого follower независима.

Терминальные `verdict`: `accepted`, `compile_error`, `compile_timeout`, `runtime_error`, `run_timeout`, `wrong_answer`, `memory_limit`, `output_limit`, `submission_timeout`, `infrastructure_error`. Ошибка загрузки файла — HTTP-ошибка до приёма, не verdict.

- Compile wall timeout — `10` секунд; wall timeout отдельного теста — `2` секунды; общий deadline активного выполнения — `60` секунд, включая создание/уборку jail, но исключая ожидание очереди. Runner самостоятельно обеспечивает deadline даже при потере worker. Followers наследуют deadline общего job, не получают новый запуск или новый бюджет. Архивная доставка после доказанного успеха не исполняет код и не продлевает sandbox.
- Причина принудительной остановки берётся из структурированного исхода sandbox, а не угадывается по stderr. При фактическом нарушении памяти/вывода — `memory_limit`/`output_limit`; при истечении общего deadline — `submission_timeout`, stage deadline — `compile_timeout`/`run_timeout`. Если общий и stage deadline совпадают, общий имеет приоритет. Сбой runner, хоста, связи или хранилища не выдаётся за ошибку программы.
- Неуспешное завершение компилятора — `compile_error`. Ненулевой exit code/сигнал запущенной программы — `runtime_error`, даже если stdout совпал с ожидаемым. Только нормальный exit `0` сравнивается с ожидаемым выводом.
- Проверка останавливается на первом провале; следующих тестов в ответе нет. `passed_tests` — число полностью пройденных тестов до него; `total_tests` — размер зафиксированного набора. Во время исполнения счётчик отражает только завершённые успешные тесты. Ошибка компиляции имеет `passed_tests: 0`. Успех имеет `passed_tests == total_tests`.
- `first_failure` присутствует при доказанном провале и инфраструктурном завершении, но не при успехе или `archive_pending`. Для invalidation это поле `null`, отдельно `state_reason: "stale_generation"` (либо `"stale_policy"` при смене политики). Старый результат не превращается в новый отрицательный verdict. Уже терминальные результаты сохраняют свой исторический контекст и показывают `stale: true`, если больше не относятся к текущему поколению/политике; они не используются как новый кэш.

### Первое нарушение и безопасная диагностика

`first_failure` имеет поля `stage` (`compile`, `run`, `submission`, `infrastructure`), `code` (тот же код, что verdict), `test_id` и `test_index` (строка и индекс с 1 либо оба `null` вне теста), `message` (русское безопасное сообщение), `diagnostics`, `stdin_preview`, `expected_preview`, `actual_preview`. Последние четыре поля — объект `{text, truncated, byte_size}` либо `null`; `byte_size` — известный исходный размер захваченного значения, а не длина JSON. При ограничении захвата неизвестный полный размер — `null`, `truncated: true`.

Каждый preview ограничен первыми `4096` исходными байтами, диагностика — `8192` байтами; отдельный общий предел stdout+stderr stage — `65536` байт. Показываются только данные первого провалившегося теста; при ошибке компиляции previews теста `null`. Нельзя возвращать будущие тесты, список всех результатов, внутренние пути, секреты или служебные логи. Для инфраструктурных ошибок — общее сообщение и UUID для обращения, не внутренние данные runner или хоста.

Текст преобразуется для отображения: некорректный UTF-8 заменяется U+FFFD, управляющие символы, кроме LF и TAB, и управляющие символы направления текста отображаются видимыми `\\uXXXX`; ANSI/terminal escapes не исполняются. JSON экранируется стандартным сериализатором, HTML выводится как текст с автоэкранированием. Ни diagnostics, ни previews не становятся Markdown/HTML. Ограничения применяются до преобразования и учитывают расширение экранированного ответа. Сырые байты для сравнения не меняются.

## 4. Две базы и жизненный цикл

Все даты — UTC (`timestamptz` в будущей реализации), UUID и digest типизированы/валидируются на границе. Ниже схема полей и ограничений, не SQL-миграции.

### `checker_transient`

| Сущность | Поля и обязательные ограничения |
| --- | --- |
| `submissions` | `id` UUIDv4 PK; `session_id` владелец; `author_name`, `author_group` snapshot; `task_id`; неизменяемый `context`; `sha256`, `byte_size`, `source` raw bytes; `original_filename` только для безопасного отображения; `created_at`, `started_at?`, `finished_at?`, `expires_at?`; `status`, `verdict?`, `cache_hit`, счётчики, `first_failure?`, `state_reason?`; `queue_job_id?`; `proven_result?`, `archive_retry_at?`, `archive_attempts`, `archive_receipt_confirmed`. `source` соответствует hash и размеру. Для `finished` обязателен verdict, для `accepted` — подтверждённая квитанция; у прочих состояний verdict отсутствует. `proven_result` нужен только для доставки доказанного успеха, не для выдачи accepted до архива. |
| `result_cache` | Составной PK `result_key`; `source` raw bytes для проверки коллизий; неизменяемый контекст, окончательный результат и ограниченная диагностика; `created_at`, `expires_at`. Нет полей автора/сессии. Допускает только кэшируемые verdict. Повторное чтение не продлевает TTL. |
| `queue_jobs` | `id` UUID PK; `result_key`, неизменяемый контекст и source; `state` (`queued`, `claimed`, `finished`, `invalidated`); `created_at`, `claimed_at?`, owner/lease планировщика, execution deadline, результат/причина завершения. Уникальность `result_key` среди `queued`/`claimed` обеспечивается БД. Followers — ссылки submissions, а не копии job. Claim/lease исключают двух активных владельцев. |
| `sessions` | Внутренний `id` PK; уникальный `token_hash`; `name?`, `group?`; `created_at`, `last_seen_at`, `expires_at`. Сырой session token не сохраняется. CSRF-токен вычисляется через HMAC и не требует отдельного изменяемого хэша/секрета в строке сессии. Профиль заполнен, только если оба поля допустимы. |
| `session_last_submissions` | PK `(session_id, task_id)`; `submission_id` UUID; `updated_at`. Ссылка может пережить TTL submission: это намеренно оставленный указатель «история недоступна», не каскадное удаление всей карты. Нельзя ссылаться на посылку другой сессии. При конкурентных приёмах побеждает последняя зафиксированная транзакция приёма; блокировка строки сессии сериализует обновления. |
| Метаданные каталога | Поколения и неизменяемые snapshot: `snapshot_id`, Git commit, tests digest, generation, текущая ссылка, политика и время публикации; данные для получения одного согласованного контекста. Снимок, нужный незавершённому job, не удаляется. Детали структуры — в [каталоге](catalog.md). |

Срок хранения терминальной submission вместе с source и диагностикой — `24` часа от `finished_at`; `invalidated` получает время завершения и такой же TTL. Кэш живёт `24` часа от создания, но смена поколения/политики делает его немедленно недоступным независимо от TTL. Очистка удаляет завершённые jobs после удаления/отсоединения их посылок; source job не должен переживать требуемые ссылки без необходимости. Истёкшие cache entries удаляются независимо от посылок. Незавершённые jobs и `archive_pending` нельзя молча удалять по TTL терминальных записей: их сначала восстанавливают, завершают либо инвалидируют.

Профиль и карта последних задач живут по TTL **сессии 30 дней**, независимо от TTL результатов. TTL сессии скользящий: валидный запрос этой сессии продлевает серверное время и cookie до 30 дней; новая сессия не получает права старой. Истечение сессии лишает доступа к её посылкам; оставшиеся исполнения могут завершиться с уже зафиксированным snapshot автора. Служебный идентификатор владельца можно хранить до очистки связанных submissions, но token/profile удаляются по TTL. Изменение tests не удаляет профиль, сессию или карту последних задач.

При отсутствии submission по сохранённому указателю профиль возвращает её UUID с `available: false`. UI пишет «История недоступна»; не восстанавливает verdict из cookie, localStorage, архива или кэша другого пользователя. При прямом GET истёкшего UUID — одинаковый `404`.

При очистке transient-результатов после смены generation указатели `session_last_submissions` сохраняются, как и профиль. Если соответствующая submission удалена, `available: false`; если ещё хранится, доступен её DTO с признаком устаревания/состоянием invalidated. Нельзя каскадно очистить карту вместе с результатами.

### `checker_archive` — постоянный архив успехов

| Сущность | Поля и уникальность |
| --- | --- |
| `blobs` | PK `(sha256, byte_size)`; `source bytea` — исходные байты, `created_at`. Файлы до 100 КиБ хранятся непосредственно в PostgreSQL, не во внешнем object storage. При конфликте ключа обязательно сравнить bytes; несовпадение — аварийный отказ без перезаписи. |
| `accepted_solutions` | Уникальность `(task_id, tests_digest, judge_policy_digest, sha256, byte_size)`; ссылка на blob, полный неизменяемый контекст первого исторического успеха, `first_accepted_at`. Один blob может иметь связи с несколькими задачами/наборами тестов. Числовой generation временной БД не является постоянным ключом: после потери ephemeral storage он может начаться заново. Контекст первого успеха не переписывается на «последний». |
| `success_receipts` | `submission_id` UUID PK, ссылка на accepted_solution, полный контекст именно этой отправки, snapshot `author_name`, `author_group`, `submitted_at`, `accepted_at`; минимально необходимый внутренний идентификатор происхождения без session token. Отдельная квитанция каждой принятой успешной посылки, включая cache hit и follower. Повтор с тем же UUID должен совпадать по blob/context/автору; конфликт — ошибка, не UPDATE автора. |

Архив не имеет автоматического TTL; он хранит исторические успешные исходники и факты самоназванных авторов/групп. Изменение tests не стирает архив и не превращает его в result cache нового поколения. Архив не публикует исходники. Политика административного доступа и обращения с персональными данными обязательна до реального ввода сервиса.

### Финализация без межбазовой транзакции

1. Worker сохраняет доказанный успех и контекст в transient как `archive_pending`; исполнения больше нет. Каждый follower имеет собственное состояние доставки и UUID квитанции.
2. Shared generation lock защищает transient-переходы: проверку текущего поколения/политики и сохранение `archive_pending`, а после архивной записи — повторную проверку и публикацию результата. Catalog-sync использует соответствующий exclusive lock при смене поколения. Это общая межпроцессная блокировка в transient PostgreSQL, не локальный mutex. На время сетевого I/O к архиву lock освобождается: публикация нового каталога не зависит от доступности второй БД. Исторический контекст архивной операции при этом неизменяем.
3. Одна транзакция archive идемпотентно проверяет/добавляет blob, accepted_solution и success_receipt. Только после её подтверждённого commit worker заново захватывает shared generation lock и отдельной transient-транзакцией выставляет `finished/accepted` и result cache, если контекст ещё актуален и посылка существует. Иначе сохраняется инвалидирование/удаление, а архивный факт остаётся историческим. Нельзя отвечать окончательным accepted на основании отправленного, но не подтверждённого upsert.
4. Сбой архива оставляет `archive_pending`, `proven_result` и данные для повтора. Повторы с backoff (1, 2, 4, 8, 16, затем не чаще раза в 30 секунд) не компилируют и не запускают программу. Каждый повтор под shared lock заново проверяет актуальность контекста; после invalidation новые повторы запрещены. Если archive commit произошёл, а transient commit потерян, повтор текущего поколения проверяет ту же квитанцию и завершает публикацию. Ошибка архива не становится wrong_answer или compile_error.
5. После перезапуска планировщик восстанавливает `archive_pending` и просроченные leases. Для незавершённого исполнения без доказанного результата сначала подтверждается отсутствие старых sandbox; если надёжно восстановить результат невозможно, job и followers завершаются `infrastructure_error`, без кэша. Нельзя параллельно продолжать старый и новый запуск с одним job.
6. Смена tests под exclusive lock инвалидирует незавершённые записи старого поколения, **включая `archive_pending`**, и отменяет их повторы. Если archive commit уже был, но публикация transient не состоялась до смены поколения, историческая квитанция может остаться в архиве; после смены старую посылку всё равно нельзя публиковать как актуальный accepted. Финализация после восстановления заново проверяет поколение. Аналогично применяется смена judge policy. Остальные детали отмены sandbox — в [безопасности](security.md).

**Потеря блокировки и неопределённый COMMIT.** Общей транзакции двух баз нет и не требуется; distributed finalize-intent и барьер публикации каталога на архив не вводятся. Если worker потерял transient-соединение/lock, а уже начавшийся archive COMMIT завершился после смены поколения, это допустимая запись исторического успеха с исходным неизменяемым контекстом. Нельзя продолжать отменённые тесты ради архива, начинать новые archive retries инвалидированной посылки или переписывать контекст квитанции на новое поколение. После восстановления worker проверяет generation под transient lock: устаревшая незавершённая посылка остаётся `invalidated`, никакие `accepted` и result cache для неё не публикуются. Наличие исторической квитанции не отменяет invalidation; недоступная по TTL запись отображается как «История недоступна». При доступном текущем контексте неопределённость разрешается идемпотентным upsert той же квитанции перед transient-публикацией.

## 5. Сессия, профиль и CSRF

Cookie содержит только случайный непрозрачный session token (не менее 256 бит энтропии), а не имя, группу, JSON истории или verdict:

`Set-Cookie: __Host-checker_session=<token>; Secure; HttpOnly; SameSite=Lax; Path=/; Max-Age=2592000`

Атрибут `Domain` отсутствует. В БД хранится криптографический хэш токена, не токен. Транспорт — HTTPS. Token, CSRF и исходник не попадают в URL/журналы. Отсутствующая/недействительная/истёкшая cookie создаёт новую пустую сессию на странице или profile GET; это не восстанавливает доступ к предыдущей. Ответы с профилем/посылками используют `Cache-Control: no-store`, не разделяемый HTTP-кэш.

`name` — непустая строка до 120 Unicode code points, `group` — до 64; обрезаются начальные/конечные пробелы, запрещены управляющие символы и символы управления направлением текста. После обрезки оба поля обязательны для submit. Никакой транслитерации и проверки реального имени нет. Профиль сохраняется целиком через PUT; его изменение не переписывает авторов прежних submissions/receipts.

Все мутации (`PUT`, `POST`) требуют `Origin`, точно совпадающий с обязательным `PUBLIC_ORIGIN` (scheme/host/port), и сессионный CSRF-токен в `X-CSRF-Token`. Отсутствующий/неверный Origin, `Origin: null` или токен — `403 csrf_failed`; CORS не разрешает чужие origins. Токен — base64url без padding от HMAC-SHA256 с обязательным серверным `CSRF_SECRET` по UTF-8 строке `checker-csrf-v1:` и каноническому стабильному внутреннему session id. Проверка — constant-time comparison. Секрет хранится вне БД; токен и отдельный csrf hash в БД не нужны. Токен получают из same-origin HTML или `GET /api/profile`, клиент хранит его только в памяти страницы. Он стабилен в рамках сессии, поэтому вкладки не инвалидируют друг друга. Пустые `PUBLIC_ORIGIN`/`CSRF_SECRET` недопустимы при запуске. SameSite не заменяет эту проверку.

Любой GET UUID проверяет ownership по сессии; UUID не bearer credential. Чужой, неизвестный и истёкший UUID дают неразличимый `404 submission_not_found`. Сервер никогда не доверяет присланному verdict, автору чужой посылки или данным истории из cookie.

## 6. HTTP

Все `/api/*` ответы — JSON UTF-8. Неизвестные JSON-поля PUT и лишние multipart-поля POST отвергаются `422`. Даты — ISO 8601 UTC. HTML-страницы не являются API загрузки исходников.

| Метод и путь | Контракт |
| --- | --- |
| `GET /` | Русская серверная Jinja-страница тем из одного опубликованного снимка, профиль и навигация. Без каталога — HTML `503` с объяснением; валидный прежний snapshot продолжает обслуживаться при неудачном sync. |
| `GET /topics/{topic_id}` | Страница темы и задач; неизвестный id — `404`; нет каталога — `503`. |
| `GET /tasks/{task_id}` | Условие, пояснения, подсказки, форма, последняя собственная посылка. Неизвестная задача — `404`; известная неактивная — `200`, причина недоступности и disabled submit. API приёма для неё отвечает `409`. |
| `GET /api/catalog` | `200 {snapshot_id, generation, topics: [...]}`; темы `{id, title, tasks:[{id,title,availability,reason}]}`. Включает известные неактивные задания с availability/reason согласно [каталогу](catalog.md), без tests, expected output, внутренних путей. Нет готового снимка — `503 catalog_unavailable`. |
| `GET /api/profile` | Создаёт/продлевает сессию, возвращает `{profile:{name,group}, csrf_token, last_submissions:[{task_id,id,available}]}`. Незаполненные поля — `null`. Карта содержит только эту сессию. |
| `PUT /api/profile` | JSON `{name,group}`, CSRF; `200` с тем же форматом, что GET. Неправильный тип/длина/пустое поле — `422 invalid_profile`; иной Content-Type — `415 unsupported_media_type`. |
| `POST /api/tasks/{task_id}/submissions` | Multipart и CSRF, заполненный профиль. `202` для нового job/follower или `archive_pending`; `200` только для уже завершённого результата из кэша после необходимых архивных записей. Ответ — submission DTO, `Location: /api/submissions/{id}`. Нет каталога — `503`; неизвестная задача — `404 task_not_found`; известная неактивная — `409 task_inactive`; полный буфер — `503 queue_full`. |
| `GET /api/submissions/{uuid}` | Собственный DTO `200` в любом состоянии; ownership/отсутствие/истечение — одинаковый `404`. Синтаксически неверный UUID тоже `404 submission_not_found`, без выдачи деталей маршрутизатора. |
| `GET /health/live` | `200 {status:"alive"}`, если web-процесс способен отвечать; не проверяет sandbox запуском пользовательского кода. |
| `GET /health/ready` | `200 {status:"ready"}` только при доступности transient, archive, пригодного опубликованного каталога и зарегистрированного работоспособного планировщика/обязательных зависимостей; иначе `503 {status:"not_ready"}`. Без секретов и внутренних адресов. Полная очередь сама по себе не провал readiness. |

Недопустимый Content-Type POST — `415 unsupported_media_type`. Ошибки до приёма: `413 request_too_large` / `source_too_large`; `415 unsupported_extension`; `422 invalid_multipart`, `missing_file`, `multiple_files`, `unexpected_field`, `invalid_filename`, `profile_required`; `403 csrf_failed`; `503 catalog_unavailable`, `queue_full`, `storage_unavailable`, `identity_conflict`. На `503 queue_full` клиенту даётся `Retry-After: 3`, повтор выполняется только по явному действию пользователя, не автоматическим POST. При нескольких ошибках приоритет: ранняя защита доступа/Origin, невозможность чтения тела/превышение лимита, структура multipart/имя/расширение, профиль и состояние каталога/приём. Любое превышение фактически прочитанного body прекращает чтение немедленно.

Общий формат ошибки до приёма (ключ `submission` всегда `null`, UUID не выдаётся):

```json
{
  "error": {"code": "source_too_large", "message": "Размер файла превышает 102400 байт.", "limit_bytes": 102400},
  "submission": null
}
```

Поле `limit_bytes` присутствует только для размеров. Успешные ответы содержат непосредственно DTO, не error-envelope. HTTP `200/202` описывает приём/чтение, а не правильность программы: `finished/wrong_answer` тоже возвращается `200` на GET и на завершённом cache hit.

### Submission DTO

| Поле | Тип и правило |
| --- | --- |
| `id`, `task_id` | UUIDv4 посылки и строковый id задачи |
| `status`, `verdict` | Состояние и nullable verdict из раздела 3 |
| `cache_hit` | Boolean, фиксируется при приёме; для follower false |
| `generation` | Целое, совпадает с `context.generation` |
| `context` | Неизменяемый объект ниже; без внутренних адресов/секретов |
| Поля digest в `context` | `runner_image_digest` — immutable image digest вида `sha256:` + 64 строчных hex; `sandbox_profile_digest`, `tests_digest`, `judge_policy_digest`, `flags_digest` — SHA-256 из 64 строчных hex. Остальные поля контекста и лимиты сохраняют описанные здесь типы и смысл. |
| `first_failure` | Nullable объект из раздела 3 |
| `passed_tests`, `total_tests` | Неотрицательные целые, первое не больше второго |
| `created_at`, `finished_at` | Время приёма и nullable терминальное время |
| `stale`, `state_reason` | Boolean актуальности контекста и nullable причина invalidation |
| `queue_position` | Позиция ожидающего уникального job с 1, одинаковая у followers; `null` вне очереди. Это мгновенная оценка, не обещание времени старта. |

Пример `202` (digest и UUID приведены как пример формата):

Id задачи — непрозрачный SHA-256 id из [каталога](catalog.md), 64 строчных hex-символа; при конструировании URL его кодируют, не интерпретируют как путь файловой системы. Путь задания в Git не является HTTP id и не принимается вместо него.

Приватный API runner не меняет публичные HTTP-маршруты, статусы или схему результата: в контексте используются указанные выше `runner_image_digest` и `sandbox_profile_digest`. Runner получает от worker только исходник и stdin текущего теста; сравнение с expected output и формирование публичного DTO остаются у worker.

Пример значения `first_failure` для `finished/wrong_answer` (в полном DTO сохраняются все остальные поля и контекст; `passed_tests: 1`, `total_tests: 3`):

```json
{
  "stage": "run",
  "code": "wrong_answer",
  "test_id": "02",
  "test_index": 2,
  "message": "Вывод не совпал с ожидаемым в тесте 2.",
  "diagnostics": null,
  "stdin_preview": {"text": "2\n", "truncated": false, "byte_size": 2},
  "expected_preview": {"text": "4\n", "truncated": false, "byte_size": 2},
  "actual_preview": {"text": "5\n", "truncated": false, "byte_size": 2}
}
```

Для `compile_timeout` — `stage: "compile"`, оба test-поля и previews `null`, message «Компиляция превысила 10 секунд». Для `run_timeout` — текущие test-поля и message «Выполнение теста превысило 2 секунды». Для `submission_timeout` — `stage: "submission"`, test-поля заполняются только если deadline настиг активный тест. Для `infrastructure_error` — `stage: "infrastructure"`, безопасная диагностика, сообщение «Ошибка инфраструктуры проверки. Это не ошибка вашей программы».

При завершённом cache hit возвращается такой же полный DTO, но новый `id`, собственные времена, `cache_hit: true`, `status: "finished"`, `queue_position: null`; `verdict`/счётчики/first_failure соответствуют результату кэша. Успех имеет `verdict: "accepted"`, `first_failure: null`. При `archive_pending` все тесты уже пройдены, но `verdict: null`, `finished_at: null`, polling продолжается. Для `invalidated` — `verdict: null`, `state_reason: "stale_generation"`, `stale: true`, `finished_at` заполнено; UI предлагает новую отправку, не автоматический запуск.

## 7. Русский интерфейс без реализации шаблонов

- Серверный рендер Jinja2, обычные страницы и vanilla JavaScript `fetch`; SPA, Node.js и клиентский Markdown-рендер не нужны. Список тем → список задач → задача; везде заголовок и хлебные крошки с обычными ссылками.
- На задаче — санитизированный Markdown условия, пояснения и отдельные раскрываемые подсказки. Политика Markdown — в [каталоге](catalog.md). Каждая подсказка использует собственные семантические `details/summary`, независимо раскрывается, работает с клавиатуры и видимым фокусом. Альтернативный JavaScript-аккордеон не нужен. Не вкладывать интерактивные элементы в недоступные кликабельные контейнеры.
- Компактная форма: «Имя», «Группа», «Файл .c», «Отправить». `accept=".c"` — только подсказка picker, не валидация безопасности. Рядом текст «Один файл .c, до 102400 байт включительно» и предупреждение, что имя/группа не удостоверяются и успешный код сохраняется в закрытом постоянном архиве.
- Профиль сохраняется PUT до отправки файла; ошибка PUT не запускает POST. Ввод не теряется при ошибке. Кнопка блокируется на время текущего browser request против случайного double-click; это не защита сервера, не гарантия одной посылки и не замена ограничениям/CSRF. После принятия можно явно отправить новую посылку; старая не отменяется.
- Блок результата показывает собственный UUID (доступный для копирования), очередь/состояние, число пройденных тестов и первую ошибку; success не смешивается с «ожидаем сохранения в архив». Русские подписи различают «Ошибка компиляции», «Таймаут компиляции», «Ошибка выполнения», «Таймаут теста», «Общий таймаут», «Превышена память», «Превышен вывод», «Неверный ответ», «Ошибка инфраструктуры», «Результат устарел». Для infrastructure error явно сказано, что это не ошибка студента. Для кэша — «Результат из кэша», без ссылки на автора.
- Polling GET только собственного UUID: первые 10 секунд после приёма раз в 1 секунду, затем раз в 3 секунды; следующий запрос начинается после завершения предыдущего. На временную сетевую/503 ошибку показывается уведомление, polling продолжается раз в 3 секунды; POST автоматически не повторяется. На terminal state polling останавливается, на `404` — «История недоступна», тоже остановка. Статусы можно озвучивать через `aria-live="polite"`, не перехватывая фокус на каждом обновлении.
- Reload получает профиль и карту last-submission с сервера. На странице задачи восстанавливается последняя собственная запись и polling, если она незавершённая. Истёкшая запись не превращается в «не отправлял» или старый успех из browser cache. После смены поколения виден исторический/устаревший контекст и приглашение отправить заново; исходник без явного выбора файла не восстанавливается и не пересылается.
- Ожидаемый/полученный вывод, stdin и диагностика — ограниченные экранированные текстовые блоки первого провала. Имя файла и профиль тоже автоэкранируются. Исходники не публикуются даже при успехе; показывается только статус и безопасные данные этой сессии.
